### P1-3 未定义不可信远端目录项到本地落盘的路径安全规则

- 位置：`docs/spec/changes/next-development.md:149,253-257,274-284,476-478,514-520`
- 事实依据：Spec 约束了调用方传入的虚拟路径和上传批量相对路径，却没有约束 FTP/SFTP 返回的目录项 `name` 如何用于递归远程拼接和 `download_dir` 本地路径构造。现有实现已有 `join_remote_child()` 对空名称、`.`、`..`、斜杠、反斜杠和 NUL 的防护（`src/ft_ftp_mcp_stdio/paths.py:20-24`），说明该边界真实存在；现有下载会把相对路径直接分段传给 `Path.joinpath`（`service.py:269-286`）。
- 影响：若重构时只按 Spec 实现，恶意或异常服务器返回的 `../x`、绝对名称、分隔符或平台特殊名称可能造成 staging 目录逃逸、覆盖本机文件、错误递归或路径泄露。该风险位于下载完整性和虚拟 root 的安全边界内，不能依赖现有辅助函数偶然保留。
- 建议：把服务器目录项明确视为不可信输入；规定名称拒绝集合、远程 child 拼接规则、本地目标规范化及“解析后必须仍位于本次随机 staging 根内”的二次校验。定义非法条目在单项/批量中的稳定错误或跳过语义，并加入恶意目录项、平台绝对路径、盘符/UNC、保留名和嵌套逃逸测试。

### P1-4 上传临时对象与最终提交没有协议级事务语义

- 位置：`docs/spec/changes/next-development.md:363-380,405-417,466-472,526-527`
- 事实依据：Spec 要求流式超限时最终目标不变、临时文件被确认清理，完整上传后才“提交”为最终目标，但没有规定临时名称的不可冲突性、创建方式、同目录要求、提交命令、`overwrite=false/true` 的竞态行为，或 FTP/SFTP 不同 rename/replace 能力下的降级策略。现有 driver 只支持直接以 `wb` 写最终路径和普通 rename（`drivers/base.py:30,35`；`drivers/sftp.py:121-134,177-181`），因此这些保证不是现有抽象自然具备的。
- 影响：实现可能在覆盖上传时先删旧文件、覆盖他人临时对象、在提交竞态中替换并非快照中的目标，或在响应丢失后既无法恢复旧文件也无法判断最终对象。会导致用户数据丢失，并使 `remote_committed:false` 和 `outcome_unknown` 契约失真。
- 建议：为 FTP 与 SFTP 分别定义 upload transaction：临时对象命名/独占策略、必须与目标同目录、flush/close、提交前目标身份复核、无覆盖提交、覆盖提交（是否允许非原子备份交换）、失败清理和残留发现。若协议/服务器无法满足覆盖保护，应明确拒绝 `overwrite=true` 或把不可保证场景定义为 `outcome_unknown`，不能承诺最终目标未改变。补充提交前断线、临时写入断线、rename 响应丢失、并发创建/替换和清理失败测试。

### P1-5 `delete` 响应丢失后的成功判据不可由所列证据证明

- 位置：`docs/spec/changes/next-development.md:452-474,543-544`
- 事实依据：第 15 节要求只有能证明“删除的是操作前同一对象”才确认成功，并称 FTP `unique` fact 可作为 delete 的身份核验证据。但删除成功后对象已经不存在，客户端无法再次取得该对象的 `unique`；“操作前 unique + 操作后路径不存在”仍不能证明是本请求删除，而不是并发删除、替换后再删除。Spec 没有服务端操作 ID、审计日志或事务回执作为因果证据。
- 影响：实现者可能把目标不存在误判为 delete 成功，违反 Spec 自己禁止的弱证据规则；或者不同实现会在相同故障下返回成功与 `outcome_unknown`，破坏公共错误契约。
- 建议：明确在当前 FTP/SFTP 能力模型下，delete 请求发出后响应丢失一律返回 `outcome_unknown`；FTP `unique` 仅用于操作前身份和检测仍存在/被替换，不足以证明已由本调用删除。只有未来引入可关联的服务端事务/审计证据后，才允许确认响应丢失的 delete 成功。

### P1-6 本地上传符号链接承诺缺少可实现的竞态与 Windows reparse 边界

- 位置：`docs/spec/changes/next-development.md:162-177,363-370,517-520,570-572`
- 事实依据：Spec 要求 `upload_dir` 对本地根路径及条目“不读取”符号链接，但只详细规定了 SFTP 远端逐段 `lstat`；没有规定本地根的每级祖先检查、最终文件打开时的 no-follow/句柄后复核、Windows junction/reparse point 行为，或检查到打开之间被替换时如何 fail-closed。残余风险只记录 SFTP 远端 TOCTOU，没有记录本地对应竞态。现有 `os.walk(..., followlinks=False)` 仍可能列出文件链接，随后普通 `open()` 会跟随它（`service.py:403-425,334-342`）。
- 影响：远端恶意指令诱导上传的场景中，链接或检查后替换可能读取并外传上传根之外的本机文件；跨平台实现也会对 junction 和中间目录链接产生不一致行为。
- 建议：明确本地路径的逐段与最终对象规则，优先使用不跟随链接/重解析点的打开方式并在打开后基于句柄复核对象；对平台无法提供可靠保证的场景 fail-closed。覆盖根链接、中间目录链接、文件链接、junction、断裂链接和检查后替换测试；若无法完全消除竞态，必须在残余风险中准确披露。

### P1-7 批量上传的不确定写结果被编码为普通成功，但宿主门禁没有验证该路径

- 位置：`docs/spec/changes/next-development.md:286-293,328-333,467,508-545`
- 事实依据：单项写结果不确定时，`upload_dir` 返回 `isError=false`、`ok:true`、`status:indeterminate`；而真实宿主门禁只明确验证 `isError=true` 时 Agent 能否获得 `error_type` 和详情（84、541），没有验证 Codex/WorkBuddy 是否会识别这个“成功结果”中的不确定状态、向用户告警且不整体重跑。
- 影响：客户端或 Agent 可能只依据 MCP 成功位和 `ok:true` 宣称上传完成，或自动重复整批上传，正好绕过本轮危险写恢复的核心目标。
- 建议：优先把含不确定项的批量结果设计成 MCP 错误，同时保留可定位的批量详情；若坚持成功分支，必须把两个正式宿主对 `status:indeterminate` 的稳定识别、用户呈现和禁止整批重跑纳入阻塞性交互测试，并在工具描述中明确该语义。

### P2-1 known-hosts/TOFU 持久化契约和故障验证不完整

- 位置：`docs/spec/changes/next-development.md:198-206,523-524`
- 事实依据：Spec 要求认证前判断且原子、并发安全持久化，但未明确记录键（alias/host/port/算法）、文件格式和权限、损坏/重复记录处理、配置指纹模式是否也写 known-hosts、跨进程锁和原子 replace 的耐久性。现行配置规范规定 alias 行格式且配置指纹首次连接也写入，最新文字只明确无配置指纹时使用 TOFU，存在解释空间。验收标准也没有并发、崩溃中断、只读目录、损坏文件和权限测试。

### P2-3 回滚方案没有覆盖本轮会修改的外部状态

### P2-4 `list_servers` 的缺失配置特例需要明确配置加载边界

- 位置：`docs/spec/changes/next-development.md:90,124-126,509-511`
- 事实依据：Spec 要求配置文件不存在时只有 `list_servers` 成功返回空列表，其他工具返回 `invalid_config`。现有所有工具统一通过 `_service() -> FileService(load_config())` 加载配置（`server.py:43-44`），而 `load_config()` 对缺失文件直接报错（`config.py:45-52`）。Spec 未规定仅该工具使用容错解析，还是引入可表示“缺失但非非法”的配置加载结果。

### 新问题

#### P1-1 `overwrite=false` 与临时对象创建仍存在可导致覆盖的数据竞态

- 位置：`docs/spec/changes/next-development.md:396-406,558,605`；`docs/decisions/0005-safe-upload-commit.md:22-29,46-51,53-60`；`docs/development/plans/next-development.md:150-155,254`
- 事实依据：临时对象规则是“创建前检查冲突，已存在时生成新名称”，但没有要求以协议支持的独占创建原子地取得该名称；检查后、实际打开前仍可能出现同名对象。更关键的是，`overwrite=false` 只在上传前和提交前检查最终目标，然后执行普通 rename，并明确接受检查与 rename 之间的竞态。FTP/SFTP 服务器的 rename 可能替换已经存在的目标；若另一写入者在最后一次检查后创建或替换目标，本调用可能在 `overwrite=false` 下覆盖它。现有 A23 仅继承“并发目标出现”测试，并未要求服务器缺少原子 no-replace 能力时拒绝提交。
- 影响：默认拒绝覆盖的公共契约可能在并发下失效，导致其他调用或用户刚写入的数据丢失；临时名称也可能覆盖或接管不属于本调用的对象。这不是单纯缺少事务隔离，而是违反 `overwrite=false` 的核心数据完整性保证，因此不能仅登记为已接受残余风险。
- 建议：临时对象必须通过原子独占创建取得，不能以“检查后普通创建”代替；若协议或服务器不能提供独占创建，必须 fail-closed。`overwrite=false` 必须只使用能够原子保证目标不存在的提交原语；driver 无法确认原子 no-replace 能力时应保持临时对象可清理并返回 `policy_rejected`，不得执行可能覆盖的 rename。`overwrite=true` 继续使用独立的原子 replace 能力门禁。分别为 FTP/SFTP 增加临时名称抢占、检查后并发创建、no-replace 有/无能力、replace 有/无能力和提交响应丢失测试，并将这些要求写入 A23。

### 上传提交契约复核

- **首次目标检查：** Spec §13.1 和 ADR 0007 都把 `overwrite=false` 定义为每文件传输前的一次授权快照。首次检查存在即 `policy_rejected`；不存在即授权后续普通 rename。两者均明确禁止提交前二次检查，且不要求原子 no-replace。
- **已接受目标竞态：** Spec §13.1、§19 和 ADR 0007 明确说明，首次检查后其他来源创建或替换同名目标时，普通 rename 可能覆盖，也可能被服务器拒绝；这不被描述为违反本项目定义的 `overwrite=false`。该风险已被准确披露，没有残留“并发下绝对不覆盖”的暗示。
- **临时对象：** 名称固定为同目录 `.<目标文件名>.ft-upload-<16 位小写十六进制>.tmp`，使用密码学安全的 64 位随机值；创建前检查冲突，最多尝试 3 次，三次均冲突返回 `server_error`。文档明确不要求协议级原子独占创建并接受检查后被占用或替换的竞态。
- **提交与错误：** 完整写入、未超限、句柄关闭和必要校验通过后才允许 rename。明确目标冲突为 `policy_rejected`，其他明确 rename 失败为 `server_error`；响应丢失不得重放并返回 `outcome_unknown`。失败清理只针对本次生成的确切临时路径，不扫描或删除归属不明对象。
- **严格覆盖路径：** `overwrite=true` 仍只允许 driver 已确认支持的不预删旧目标的安全原子替换；能力未知或不支持时 `policy_rejected`，没有因兼容性决策而放宽。
