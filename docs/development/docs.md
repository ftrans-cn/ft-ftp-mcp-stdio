# 文档、决策记录与注释规范

## 文档原则

文档应与可验证的代码、配置和测试一致，明确区分已实现事实、计划和假设。公共契约或用户行为发生变化时，应在同一任务中更新对应文档。

产品需求、配置规范、MCP Schema 和用户手册是各自领域的事实来源；同一事实尽量只在一个位置完整定义，其他文档通过引用建立关系，避免复制后漂移。

过程规范使用稳定文件名并纳入 Git。带版本号的产品或契约文档可以保留历史版本；评审报告和测试报告必须标明适用基线，历史报告不能作为当前状态的证明。

## 同步要求

- 能力范围或验收标准变化：更新 PRD 和相关测试。
- 配置项、默认值、凭据或路径规则变化：更新配置规范、样例和用户手册。
- 工具名称、参数、返回值或描述变化：更新 MCP Schema、测试和用户手册。
- 安装、构建或客户端接入变化：更新用户手册及相关脚本说明。
- 版本、标签、产物或发布流程变化：更新 `docs/release.md` 和发布说明。

## 架构决策记录

对长期影响架构、安全边界、公共契约或运维方式且存在明显取舍的决策，创建 ADR：

```text
docs/decisions/NNNN-short-title.md
```

编号使用四位递增数字。状态使用 `Proposed`、`Accepted`、`Rejected` 或 `Superseded`。ADR 至少记录背景、候选方案、决定、理由、后果和关联资料。

已接受的 ADR 不直接改写结论；后续决策发生变化时创建新 ADR，并在新旧记录中标明取代关系。

## 代码注释

不要求完整逐行注释。优先通过清晰的命名、类型和结构表达代码；注释只说明代码本身难以表达的原因、约束、安全边界、协议细节或反直觉行为。

公共接口的说明应准确描述契约、重要参数、返回值、副作用和异常。注释必须随代码更新，不保留失效叙述、重复实现细节或大段被注释掉的旧代码。若一段代码必须依赖大量注释才能理解，应先考虑简化实现。
