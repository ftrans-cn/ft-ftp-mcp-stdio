# 风险、验证与审查规范

## 风险分级

开始实现前按最高影响确定等级：

- **普通变更**：不改变安全边界、公共契约、数据完整性或发布状态。由实现者自审并执行相关验证。
- **敏感变更**：涉及安装、依赖、错误契约、兼容性、构建流程或跨模块行为。实现前说明风险，完成后检查完整 diff 并扩大验证；条件允许时由独立上下文复审。
- **高影响变更**：改变认证或凭据处理、路径隔离、删除保护、数据完整性、公共 MCP/配置契约，或形成正式发布。必须进行实现前独立设计审查和实现后独立代码审查。

仅修改措辞或排版，不因文件名称或所属领域自动升级为高影响；等级取决于实际行为和风险。

## 验证

验证应覆盖被改变的行为和主要失败路径：

- 普通变更运行最相关的测试和静态检查。
- 敏感变更增加受影响模块、兼容性或安装构建验证，并审查完整 diff。
- 高影响变更验证安全边界、回滚路径和公共契约；发布候选还应满足 `docs/release.md`。

无法执行某项验证时，应说明原因、替代证据和残余风险，不得把“未运行”等同于“已通过”。

## 实现前独立设计审查

主代理先形成可审查的方案，至少包含目标、非目标、约束、接口或数据变化、主要风险、验证和回滚思路。第二代理在独立上下文中仅根据需求、现有规范和方案审查，不预设实现正确。

第二代理按严重级别提出问题。主代理负责核对事实并修订方案；若修订改变安全边界、公共契约或核心设计，应再次交由第二代理复审，直到 P0/P1 问题关闭或明确提交用户裁决。一般措辞和低风险细节不需要反复往返。

## 实现后独立代码审查

主代理完成实现、自测和自审后，固定候审快照并记录：

- `Start SHA`：本任务开始时的明确提交。
- `Candidate SHA`：待审查的明确提交。
- 审查范围：`git diff <StartSHA> <CandidateSHA>`。

只有审查相对可能分叉的目标分支时才使用三点 diff。候审期间不改写 Candidate；修复意见使用新提交，使审查轨迹可见。独立审查者重点检查正确性、安全性、兼容性、测试缺口和文档一致性，并以 P0 至 P3 标注严重程度。

P0/P1 必须在合并或发布前解决，或由用户明确接受。修复改变核心设计或引入新的高影响行为时，再进行一轮独立审查。

## 审查不可用

独立审查者不可用时，本地实现可以继续，但不得宣称已完成独立审查。主代理应扩大测试、重新以独立视角审查完整 diff，并记录降级原因和残余风险。高影响变更仍不得在缺少必要批准时合并或发布。
