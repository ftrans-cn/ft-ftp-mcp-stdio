# Git 与提交规范

## 权限

AI 可在实现、缺陷修复和构建任务完成并验证后创建本地提交。除非用户明确授权，不得推送、合并、变基、修改已有提交、创建标签、发布或部署。

解释、研究、诊断和评审类任务不自动提交；用户明确要求不提交时，以用户要求为准。

## 开始任务

先确认当前分支、工作区和暂存区：

```text
git status --short --branch
git diff --cached --quiet
```

若暂存区非空，默认禁止自动提交，避免把用户预先暂存的内容带入任务提交。此时应改用独立 worktree，或由用户明确指定如何处理。

存在并发任务、长期任务或需要独立审查的候选变更时，应在开始实现前创建独立分支和 worktree。不要等到工作区冲突后再隔离。

## 提交拆分

一个提交只表达一个可独立理解、验证和回滚的逻辑变更。一次批量任务可以包含多个提交，拆分依据是逻辑边界，而不是 AI 执行次数：

- 相互独立的功能、修复或基础设施变更分别提交。
- 必须同时存在才能保持可运行、可测试状态的代码、测试和文档可以合并提交。
- 纯格式化、重构与行为变更原则上分开。
- 不得为追求“一项任务一个提交”而制造无法通过验证的中间状态。

开始批量任务时先形成简短的提交映射；实施中若依赖关系变化，可调整映射并在交付时说明。

## 暂存与检查

有用户改动或其他任务改动时，不使用 `git add .`、`git add -A` 或 `git commit -a`。按明确路径或补丁暂存，仅纳入当前逻辑变更。

每次提交前检查：

```text
git diff --check
git diff --cached --stat
git diff --cached
```

确认暂存内容完整、没有秘密信息、调试残留、生成垃圾或无关文件，并完成与风险相称的验证。

## 提交信息

提交信息使用英文祈使句，标题简洁描述结果，不写执行过程。必要时在正文说明动机、兼容性或迁移影响。

## 提交后

提交后检查状态和提交内容，向用户报告提交 SHA。候选提交或共享历史不得通过 amend、rebase 或 force push 静默改写；已共享变更需要撤销时优先创建显式 revert 提交。
