# 版本与发布规范

## 权限边界

修改版本号、创建标签、构建正式产物、推送或发布都需要用户明确授权。授权其中一项不自动授权其他项。

## 版本来源与一致性

产品版本必须在以下位置保持一致：

- `pyproject.toml` 包元数据；
- 运行时版本定义；
- MCP 对外暴露的产品版本；
- Git 标签；
- 发布产物名称；
- 发布说明。

文档修订号可以独立增长，但正文标明的适用产品版本必须覆盖发布候选版本。

当前构建或安装脚本仍可能包含硬编码版本，发布前必须核对：

- `scripts/build_offline_package.ps1`
- `scripts/build_offline_wheels.ps1`
- `install.bat`

长期应由脚本从单一版本来源读取；完成该改造前，上述位置属于发布版本矩阵的一部分。

## `0.x` 版本策略

项目继续处于开发期：

- 向后兼容的缺陷修复和维护变更升级 `PATCH`。
- 新功能升级 `MINOR`。
- 经评审确认必须进行的公共契约破坏性变更也升级 `MINOR`，不得放入 `PATCH`。
- 破坏性变化必须在发布说明中明确标识，并提供迁移说明。
- 当公共契约和兼容承诺足够稳定时，再进入 `1.0.0`。

## 发布前检查

发布候选至少应完成与改动相关的：

- 自动化测试、Ruff 和 mypy；
- MCP 工具发现及 Schema 核对；
- 在受控环境中的必要 live 测试；
- 离线安装或构建验证；
- 产物内容、版本、文件名和校验值检查；
- 用户文档适用版本及发布说明检查。

仓库尚未建立 CI 时，这些检查由本地明确执行并记录结果；不得把构建脚本本身视为 CI。

## 标签与产物

未来发布标签统一使用 annotated tag，标签信息应包含版本和发布摘要。已有标签保持原状，不为统一形式而重写。

正式产物应从已审查的固定提交构建，记录提交 SHA、标签、构建环境、验证结果和文件校验值。候选提交在审查和构建期间不得被静默改写。

## 回滚

发布前应明确可执行的回滚路径。已共享或已发布的版本不得通过改写 Git 历史撤销；代码回退使用显式 revert 或后续修复版本，发布说明应记录影响、处置和替代版本。
