# ADR 0005：通过远端临时对象安全提交上传

- 状态：Superseded
- 日期：2026-09-21
- 接受日期：2026-09-21
- 关联 Spec：`docs/spec/changes/next-development.md`
- 取代者：`docs/decisions/0007-snapshot-authorized-upload-commit.md`

## 背景

> 本决定已由 ADR 0007 取代。以下内容作为历史决策记录保留，不再表示当前上传提交契约。

上传文件需要同时处理大小限制、传输中断、覆盖保护和响应丢失。直接写最终目标会在超限或中断时暴露部分内容；为了覆盖而先删除旧目标，则可能在后续上传或 rename 失败时造成数据丢失。FTP 与 SFTP 又没有统一的原子无覆盖创建和原子替换能力，不能把普通 rename 描述成跨协议事务。

## 候选方案

1. 继续直接写最终目标，失败时尽力删除部分文件。
2. 写同目录临时对象，完整传输后再提交；只在服务器支持安全原子替换时允许覆盖。
3. 写临时对象，覆盖时先删除旧目标再 rename，以换取更广泛的服务器兼容性。

## 决定

采用方案 2。

- `upload_file` 和 `upload_dir` 的每个文件先写入最终目标同目录下、不可预测且归属本次调用的唯一临时对象。
- 只有到达 EOF、未超过上传大小限制、远端句柄成功关闭且必要检查通过后，才允许提交到最终目标。
- `overwrite=false` 在上传前和提交前检查目标；已存在即拒绝。该策略不承诺消除检查与 rename 之间的多客户端竞态。
- `overwrite=true` 仅在 driver 能确认服务器支持不预先删除旧目标的原子替换时允许。能力未知或不支持时拒绝覆盖。
- 禁止采用“先删除旧目标，再移动临时对象”的降级路径。
- 提交请求发出后连接中断或响应丢失时禁止重放；证据不足时返回 `outcome_unknown`。
- 提交前失败、取消或超限时清理临时对象。清理失败或状态无法确认时，按 Spec 返回 `server_error` 或 `outcome_unknown`。
- 自动清理只能处理明确归属于本次调用的临时对象，不删除归属不明的远端文件。

## 理由

- 防止部分上传或超限内容出现在最终目标。
- 避免覆盖过程中先删除用户原文件造成不可恢复的数据丢失。
- 将服务器能力不足表达为明确拒绝，而不是以兼容性名义降低数据完整性。
- 对响应丢失保持诚实，不依赖文件名、存在性或大小相同推断成功。

## 后果

正面影响：

- 上传失败通常不会改变最终目标。
- 上传大小限制可以在流式传输中生效，而不会提交超限文件。
- 覆盖语义和 `outcome_unknown` 的边界可以统一测试。

代价与风险：

- 每个上传至少增加一次远端 rename 和若干状态检查。
- 不支持可靠原子替换的 FTP/SFTP 服务器无法使用 `overwrite=true`。
- `overwrite=false` 仍存在提交前检查与 rename 之间的协议级竞态。
- 进程崩溃或网络故障可能留下可识别的临时对象，需要经授权清理。

## 验证

- 覆盖临时名称冲突、写入前断线、写入中断、大小超限、关闭失败和清理失败。
- 验证临时对象与最终目标位于同一目录，且临时名称不返回给 Agent。
- 验证 `overwrite=false` 的上传前检查、提交前检查和并发目标出现。
- 验证 `overwrite=true` 在有、无安全原子替换能力时分别提交或拒绝，且从不先删除旧目标。
- 覆盖 rename 成功、明确失败、响应丢失和提交后状态无法核验。
- 分别覆盖 FTP、SFTP、`upload_file` 和 `upload_dir`。

## 回滚

如需恢复直接写目标或允许非原子覆盖，必须通过新的 ADR 明确接受部分文件暴露和旧目标丢失风险，并取代本决定。实现阶段的代码回退按执行清单记录的 Start SHA 执行；远端已完成写入和归属不明对象不属于 Git 回滚范围。
