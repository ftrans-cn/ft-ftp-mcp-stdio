# ADR 0003：仅保留逐文件上传大小限制

- 状态：Accepted
- 日期：2026-09-21
- 接受日期：2026-09-21
- 关联 Spec：`docs/spec/changes/next-development.md`

## 背景

当前配置同时包含单文件大小、批次文件数量和批次总字节限制，并将这些限制用于上传和下载。批次限制只能约束单次工具调用，Agent 仍可通过多次调用单文件工具完成相同总量，因此它不是任务级或账号级资源边界。与此同时，下载侧的 FTP 目录枚举可能无法可靠取得文件大小，完整预检会增加兼容性和使用摩擦。

项目仍需要阻止单个超大本地文件被意外上传，但本轮不建设任务级配额、速率限制、并发限制或全局资源治理。

## 候选方案

1. 保留单文件、批次文件数量和批次总字节限制，并在上传和下载前完整预检。
2. 只保留每个上传文件的大小限制，取消上传和下载的文件数量、批次总字节以及全部下载大小限制。
3. 取消现有限制，改为任务级配额、速率、并发和存储治理。

## 决定

采用方案 2。

- 保留服务器配置字段 `max_file_size_bytes`，默认值保持 2 GiB，仅约束上传文件。
- `max_file_size_bytes` 接受非负整数；`0` 表示不限制。
- `upload_file` 和 `upload_dir` 中的每个普通文件适用相同上限；等于上限时允许上传。
- `upload_dir` 不为大小限制预先扫描完整目录，而是在逐文件传输过程中执行实际字节计数。单个文件超限时停止该文件，安全清理远端临时文件，记入 `skipped`，并继续处理后续文件。
- 上传和下载均不设置客户端文件数量或批次总字节上限；`download_file` 和 `download_dir` 不设置客户端文件大小上限。
- 配置版本 2 删除 `max_batch_files` 和 `max_batch_total_bytes`，批量工具删除 `max_files` 参数。
- 批量结果中的 `file_count` 和 `total_size` 仅作为成功项统计，不作为限制判据。

具体错误结构、批量状态、临时文件清理要求和验收标准以关联 Spec 为准。

## 理由

- 对同一个上传文件采用同一限制，不因调用 `upload_file` 或 `upload_dir` 而改变含义。
- 单文件限制能够稳定阻止一个超大文件；批次数量和总量限制可通过多次调用绕过，不能作为全局安全保证。
- 取消下载大小预检，避免 FTP 文件大小未知或不可靠时拒绝合法下载。
- 批量逐项跳过超限文件，可以完成其余合规文件，降低整批失败带来的使用摩擦。
- 真正不可轻易绕过的资源治理应在任务、时间窗口、账号或存储层设计，不应把单次调用限制描述成全局兜底。

## 后果

正面影响：

- 配置和工具契约更简单，上传大小限制具有单一、稳定的语义。
- 下载不再依赖远端必须提供可靠文件大小。
- 批量上传不会因一个超限文件放弃其他合规文件。

代价与风险：

- 单次批量调用可以包含任意数量和任意合计大小的合规文件。
- 下载可以消耗大量时间、网络、本地磁盘和 staging 空间；上传可能耗尽远端配额或长时间占用连接。
- 大量小文件仍可能造成资源压力。
- `max_file_size_bytes=0` 会关闭客户端上传文件大小保护。
- 服务端配额、文件大小或会话限制仍可能独立拒绝操作，客户端不承诺覆盖这些限制。

上述风险由本决定明确接受。未来如需资源治理，应通过新的 ADR 设计任务级配额、并发、速率、超时或存储边界。

## 验证

- 验证 `max_file_size_bytes` 的默认值、`0`、边界值、负数和 boolean 配置行为。
- 验证 `upload_file` 和 `upload_dir` 对同一文件执行相同限制，并覆盖预检后文件增长。
- 验证 `upload_dir` 在部分或全部文件超限时继续处理、准确返回 `skipped`，且不遗留远端临时文件或改变最终目标。
- 验证上传和下载不再应用文件数量、批次总字节或下载文件大小限制。
- 验证 `file_count` 和 `total_size` 只统计成功项。

## 回滚

如需恢复批次或下载限制，必须先重新定义其保护目标、未知大小处理、逐项或整批失败语义及无法通过多次调用绕过的边界，再通过新的 ADR 取代本决定。实现阶段的代码回退仍按执行清单记录的 Start SHA 执行，并同步恢复匹配的配置 Schema、工具 Schema、测试和文档。
